PENDIENTES GRANDES (BACKEND – LÓGICA Y SEGURIDAD)
--------------------------------------------------
1) MODELO DE RESERVAS (BOOKINGS) EN MONGO
   - Colección: bookings
   - Campos sugeridos:
     - _id (ObjectId)
     - guideId (string, ej. "g1001")
     - guideName (string)
     - travelerEmail (string)
     - travelerName (opcional)
     - date (string YYYY-MM-DD)
     - hours (number)
     - amountUsd (number)
     - currency (string, ej. "USD")
     - stripeSessionId (string)
     - stripePaymentIntentId (string opcional)
     - status (string: "pending", "paid", "cancelled", "failed")
     - createdAt (Date)
     - updatedAt (Date)
   - Índices recomendados:
     - travelerEmail
     - guideId
     - status

2) ENDPOINT PARA CREAR RESERVA PREVIA AL CHECKOUT
   - Cuando la app mobile llama a /api/payments/create-checkout:
     a) Se crea una RESERVA "pending" en Mongo con los datos básicos:
        - guideId, date, hours, amountUsd, travelerEmail, status="pending"
     b) Se crea la Checkout Session en Stripe.
     c) Se guarda stripeSessionId en el documento de la reserva.
     d) Se devuelve al cliente:
        {
          ok: true,
          checkoutUrl,
          bookingId
        }

   - Esto permite:
     - Tener registro de intento de compra aunque Stripe falle después.
     - Cruzar pagos con reservas por stripeSessionId.

3) WEBHOOK Stripe → ACTUALIZAR RESERVA
   - En /api/stripe/webhook:
     - Verificar firma con STRIPE_WEBHOOK_SECRET.
     - Para eventos relevantes:
       * checkout.session.completed
       * payment_intent.succeeded
     - Buscar la reserva correspondiente por stripeSessionId o paymentIntentId.
     - Actualizar:
       - status = "paid"
       - stripePaymentIntentId
       - updatedAt = ahora
     - Si no se encuentra reserva, loggear el evento en una colección "orphanStripeEvents" para análisis.

4) ENDPOINT ADMIN SEGURO PARA LISTAR RESERVAS
   - Ruta sugerida: GET /api/admin/bookings
   - Seguridad simple pero firme:
     - Header obligatorio: x-admin-key
     - Valor: ADMIN_API_KEY definido en .env (solo el dueño lo sabe)
     - Si falta o no coincide → 401 Unauthorized
   - Filtros básicos:
     - ?status=pending|paid|cancelled
     - ?email=correo@viajero.com
   - Este endpoint NO se usa desde la app pública, solo desde un panel interno o PowerShell.

5) CORS Y SEGURIDAD ADICIONAL
   - CORS:
     - Mantener restringidos los orígenes web conocidos.
     - Las apps nativas mobile no pasan por CORS (usan HTTPS directo).
   - Rate limiting:
     - Mantener limitador fuerte en /api/payments/create-checkout y /api/stripe/webhook.
   - Headers:
     - helmet ya activado (revisar que siga).
   - Logs:
     - Log mínimo de seguridad:
       - Creación de reservas
       - Cambios de status de reservas
       - Errores en webhooks
